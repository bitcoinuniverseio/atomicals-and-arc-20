## 開始之前

- 支援的網路：mainnet。
- 狀態：協定行為。
- 預防是唯一的手段，沒有復原途徑。

## 操作步驟

<Steps>

1. 以 outpoint 與聰為單位作業，絕不要使用代幣金額輸入框。
2. 除非已為多代幣情形建立模型，否則每筆交易只移動一個代幣。
3. 當批次超過要傳送的數量時，務必包含一個著色找零輸出。
4. 把找零輸出的大小設為餘額的**精確值**。
5. 在建構之前，依序建立確切的輸入與輸出集合模型。
6. 確認計算出的銷毀數量為零。
7. 加入手續費輸入與基數找零，然後重新建立模型。
8. 確認銷毀數量仍為零。
9. 簽署之前，把錢包提示與你的模型逐行比對。

</Steps>

第七步與第八步最容易被略過，而錢包加入的找零正是在這裡悄悄改變結果。

## 四種型態，已執行

<VectorTable only={["oversized-next-output", "too-few-outputs", "first-output-too-large", "two-tokens-non-clean-fallback"]} />

| 型態 | 預防方式 |
| --- | --- |
| 下一個輸出太大 | 把找零設為餘額的精確值 |
| 輸出不足 | 務必包含著色找零 |
| 第一個輸出大於整批 | 絕不要把小批次送入大額首筆付款 |
| 多代幣回退 | 每筆交易只移動一個代幣 |

<Aside type="danger" title="傳送給不理解 Atomicals 的服務">
交易所入金地址、一般比特幣錢包，或任何不支援 Atomicals 的服務，都會把該輸出當成一般比特幣花掉。
單位就此消失，任何銷毀記錄都無法彌補。傳送之前，請確認目標方支援 Atomicals。
</Aside>

## 唯一一種刻意銷毀的情形

刻意銷毀單位是一種合法操作。請明確地進行：建構一筆恰好銷毀你所要銷毀數量的交易，確認數字並記錄
原因。絕不要依賴意外銷毀。

## 廣播之後

透過會回報銷毀的資料來源讀取該交易，確認數字與預期一致。比較著色輸入總額與著色輸出總額之和。
